JavaScript 스코프 딥다이브: ECMAScript 사양부터 V8 엔진 내부까지

자바스크립트에서 클로저나 스코프가 "왜 이렇게 동작하는지" 이해하지 못한 채 쓴 경험이 있다면, 이 글이 그 빈자리를 채워줄 것이다. ECMAScript 사양이 스코프를 어떻게 명세하는지, V8 엔진이 그것을 실제로 어떻게 구현하는지를 함께 살펴본다. 두 층을 같이 보면 "왜 JS가 이렇게 설계되었는가"가 자연스럽게 보이기 시작한다.

ECMAScript의 Environment Record

ECMAScript 사양(9.1절)은 스코프를 Environment Record라는 추상 타입으로 설명한다.

환경 레코드는 ECMAScript 코드의 렉시컬 중첩 구조(lexical nesting structure)를 바탕으로, 식별자(Identifiers)가 어떤 변수나 함수와 연결되는지를 정의하기 위해 사용되는 명세상의 타입(specification type)이다.

보통 환경 레코드는 FunctionDeclaration, BlockStatement, TryStatement의 Catch 절처럼 특정 문법 구조와 연결된다. 이러한 코드가 평가될 때마다, 그 코드에서 생성되는 식별자 바인딩을 기록하기 위해 새로운 환경 레코드가 생성된다.

[[OuterEnv]]가 존재하는 이유

모든 환경 레코드는 [[OuterEnv]] 필드를 가진다. 이 값은 null이거나, 바깥쪽 환경 레코드를 가리키는 참조다. 이 필드가 환경 레코드들의 논리적인 중첩 관계를 만든다.

inner 환경 레코드
  └── [[OuterEnv]] → outer 환경 레코드
                       └── [[OuterEnv]] → 전역 환경 레코드
                                            └── [[OuterEnv]] → null

예를 들어 하나의 FunctionDeclaration 안에 두 개의 중첩 함수가 있다면, 그 두 내부 함수의 환경 레코드는 모두 바깥 함수의 환경 레코드를 [[OuterEnv]]로 가리킨다.

한 가지 중요한 점은, 환경 레코드는 어디까지나 명세의 추상적 메커니즘이라는 것이다. 실제 ECMAScript 엔진이 이 구조를 1:1로 구현할 의무는 없다. 따라서 JavaScript 코드에서 이 값을 직접 접근하거나 조작하는 것은 불가능하다.

V8의 구현: closure → context → ScopeInfo

ECMAScript 사양이 Environment Record와 [[OuterEnv]]로 스코프를 설명한다면, V8은 이를 세 가지 개념으로 나눠 구현한다.

closure → context → ScopeInfo는 "내부 함수가 바깥 변수를 써야 할 때, V8이 그 변수를 어떻게 살려두고 나중에 다시 찾게 만드는가"를 설명하는 흐름이다.

Closure

자바스크립트 함수는 단순한 "코드 덩어리"가 아니다. 함수 리터럴을 평가할 때 생성되는 closure는 함수 코드와 current context를 함께 가리킨다. 그래서 나중에 그 함수가 다른 곳에서 실행되더라도, 자신이 만들어질 당시의 바깥 변수들에 접근할 수 있다.

Context가 필요한 이유

일반적인 함수의 지역 변수는 스택 프레임에 올려두면 충분하다. 함수가 끝나면 스택에서 같이 사라지기 때문이다.

그런데 내부 함수가 바깥 함수의 변수 x를 참조하고, 그 내부 함수가 바깥 함수가 끝난 뒤에도 살아 있다면? x를 스택에만 둘 수 없다. 그래서 V8은 내부 함수가 참조하는 바깥 변수들을 heap-allocated context에 저장한다. 이것이 렉시컬 클로저를 구현하는 핵심 메커니즘이다.

ScopeInfo

Context가 실제 값을 담는 저장소라면, ScopeInfo는 그 Context 안에 어떤 변수들이 어떤 방식으로 들어 있는지 설명하는 메타데이터다.

실제 코드로 보는 V8의 스코프 분석

예시 코드를 통해 V8이 스코프를 어떻게 분석하는지 살펴보자.

function outer(x) {
  const a = 10;

  function inner(y) {
    const b = 20;
    return x + a + y + b;
  }

  return inner;
}

outer(1)(2);

이 코드를 V8이 어떻게 평가하는지 보기 위해 d8 셸에서 다음 명령어를 실행한다.

d8 --print-scopes index.js

d8이란? V8 엔진의 개발자용 JavaScript 셸이다. Node.js가 아니라 V8 자체를 직접 실행해보는 도구로, --print-scopes 같은 플래그를 붙여 최적화, 바이트코드, 스코프, context 같은 내부 동작을 관찰할 수 있다.

결과는 아래와 같다.

Inner function scope:
function outer () { // (0x11c00e2ba28) (14, 143)
  // NormalFunction
  // 2 heap slots
  VAR x;  // (0x11c00e33248) forced context allocation, never assigned
  CONST a;  // (0x11c00e33290) forced context allocation, never assigned
  VAR inner;  // (0x11c00e33608) never assigned

  function () { // (0x11c00e332c0) (59, 118)
    // NormalFunction
    // 2 heap slots
    VAR y;  // (0x11c00e33500) never assigned
    CONST b;  // (0x11c00e33548) never assigned
  }
}

Global scope:
function outer (x) { // (0x11c00e2ba28) (14, 143)
  // will be compiled
  // NormalFunction
  // 1 stack slots
  // 4 heap slots
  VAR x;  // (0x11c00e2bc80) context[2], forced context allocation, never assigned
  CONST a;  // (0x11c00e2bd00) context[3], forced context allocation, never assigned
  VAR inner;  // (0x11c00e2bf08) local[0], never assigned

  function inner () { // (0x11c00e2bd90) (59, 118)
    // lazily parsed
    // NormalFunction
    // 2 heap slots
  }
}

Global scope:
function inner (y) { // (0x11c00e2bbd0) (59, 118)
  // will be compiled
  // NormalFunction
  // 1 stack slots
  VAR y;  // (0x11c00e2be28) parameter[0], never assigned
  CONST b;  // (0x11c00e2bea8) local[0], never assigned, hole initialization elided
}

V8이 처리하는 순서

1. outer의 스코프/함수 정보를 먼저 파악한다

V8은 inner가 outer의 변수 x, a를 참조한다는 사실을 알아내고, outer에는 context가 필요하다고 판단한다. 내부 함수가 바깥 변수에 접근하면 그 변수를 스택이 아니라 heap의 context에 둔다.

2. 전역(script) 기준에서 outer 선언을 가진다

outer가 나중에 실행될 때 context가 필요하다는 정보도 함께 들고 있다. lazy parsing 중에도 바깥 함수를 올바르게 컴파일하는 데 필요한 변수/스코프 정보를 유지한다.

3. outer를 구체적으로 파싱/컴파일할 때 저장 위치를 정한다

x, a는 inner에 의해 캡처되므로 context로 가고, inner 자체는 outer의 로컬 바인딩으로 남는다.

x     → context[2]   (heap에 저장)
a     → context[3]   (heap에 저장)
inner → local[0]     (스택에 저장)

4. inner는 처음엔 lazy/preparse 상태였다가 필요할 때 다시 파싱/컴파일된다

V8은 preparsed function이 실제 호출되면 그때 fully parsed and compiled on-demand 된다.

5. inner를 파싱하면 자기 로컬 저장 위치를 정한다

y와 b는 더 안쪽 함수에 캡처되지 않으므로 context가 아니라 로컬/파라미터로 남는다.

y → parameter[0]  (스택에 저장)
b → local[0]      (스택에 저장)

Scope vs Context

두 개념의 역할은 명확히 다르다.

ScopeContext
시점파싱/컴파일 시점런타임 시점
역할어떤 변수가 어디 선언됐는지, 어디에 배치돼야 하는지 결정그렇게 결정된 변수들 중 런타임에 오래 살아야 하는 값들을 실제로 저장
저장 위치엔진 내부 정적 구조Heap

모든 스코프가 무조건 런타임 Context를 갖는 건 아니다. 내부 함수가 참조하지 않는 일반 로컬 변수는 스택/로컬 슬롯에 두고, 캡처되는 변수만 context에 올린다. 그래서 Scope는 늘 필요하지만, Context는 필요할 때만 만들어진다.

스코프의 종류

지역 스코프

지역 스코프는 특정 함수나 블록 내부에서만 유효한 이름 공간이다. ECMAScript 사양에서는 함수 선언문, 블록문, catch 절 같은 문법 구조마다 별도의 환경이 생길 수 있다. V8에서는 이 정적 구조를 Scope로 관리하고, 필요하면 실제 값 저장은 Context로 나눠 처리한다.

지역 스코프의 핵심은 단순히 "밖에서 못 보는 변수"의 개념이 아니라, 현재 코드가 어떤 선언을 우선적으로 참조해야 하는지 정하는 기준이라는 점이다. V8 파서는 현재 스코프를 스택처럼 관리하며, 블록이나 함수가 시작되면 새 스코프를 push하고 끝나면 pop한다.

전역 스코프

전역 스코프는 가장 바깥의 최상위 스코프다. ECMAScript 사양에서는 전역 코드가 Global Environment Record 위에서 실행된다고 설명한다. 현재 함수나 블록 안에서 이름을 찾지 못하면 마지막에 전역 스코프까지 올라가서 식별자를 찾는다.

d8의 디버그 출력에서 보이는 Global scope는 "가장 바깥 기준의 스코프 리포트"에 가깝고, 실제 중첩 관계는 별도로 outer_scope/inner_scope 트리로 관리된다.

함수 레벨 스코프

함수 레벨 스코프는 함수 하나가 만드는 이름 공간이다. 전통적으로 var와 함수 매개변수는 함수 레벨 스코프에 속한다. V8에서는 함수가 파싱될 때 FUNCTION_SCOPE에 해당하는 스코프가 만들어지고, 이 안에서 파라미터와 로컬 선언의 배치가 결정된다. 앞서 d8 출력에서 본 y -> parameter[0], b -> local[0]이 바로 이 함수 레벨 스코프의 배치 결과다.

함수 내부 변수라고 해서 모두 같은 방식으로 저장되지는 않는다. 내부 함수가 참조하지 않는 값은 스택이나 로컬 슬롯에 둘 수 있지만, 내부 함수가 바깥 함수의 변수를 참조하면 그 변수는 Context에 올라간다. 따라서 함수 레벨 스코프는 선언의 범위를 설명하는 개념이고, 실제 저장 위치는 분석 결과에 따라 달라진다.

렉시컬 스코프

렉시컬 스코프는 어디서 호출되었는가가 아니라, 어디에 작성되었는가로 스코프가 결정되는 규칙이다. ECMAScript 사양도 식별자 해석을 코드의 lexical nesting structure, 즉 문법적 중첩 구조를 기준으로 설명한다.

이 원리 때문에 내부 함수는 자신이 선언될 당시의 바깥 변수를 기억할 수 있다. V8은 함수 리터럴이 평가될 때 생성되는 closure가 함수 코드와 current context를 함께 가리킨다고 설명한다. 내부 함수가 바깥 함수의 변수를 참조하면, 그 변수는 스택이 아니라 heap에 있는 Context에 저장된다. 이렇게 해서 바깥 함수가 종료된 뒤에도 내부 함수가 그 값을 계속 사용할 수 있다.

렉시컬 스코프는 사양상 추상 개념이지만, V8에서는 Scope → Context → ScopeInfo의 조합으로 구현된다.

스코프 체인

스코프 체인은 식별자를 찾을 때 현재 스코프에서 시작해 바깥 스코프로 올라가는 탐색 규칙이다. ECMAScript 사양은 이를 Environment Record와 [[OuterEnv]] 링크로 설명한다.

V8에서는 두 층으로 나뉜다.

  • 파싱 시점: Scope 트리가 outer_scope와 inner_scope 링크로 체인을 구성
  • 실행 시점: Context 체인이 실제 값 접근을 담당

예를 들어 inner 함수 안에서 a를 읽을 때, 먼저 inner 자신의 스코프에서 a를 찾고, 없으면 outer의 스코프로 올라간다. 정적 분석에서는 "a는 outer에 선언된 변수"라고 결정하고, 런타임에는 outer의 Context에서 실제 값을 꺼낸다.

스코프를 "변수 접근 범위"라는 표면적 개념으로만 알고 있었다면, 이제 그 아래에 ECMAScript 사양의 Environment Record 체인이 있고, V8이 그것을 Scope(정적 구조) + Context(런타임 값) + ScopeInfo(메타데이터)로 나눠 구현한다는 그림이 보일 것이다. 렉시컬 스코프와 클로저가 왜 그렇게 동작하는지도, 이 그림을 알면 자연스럽게 따라온다.
