JavaScript Class 완전 정복: prototype, private, this, 그리고 V8 최적화까지

class User {}를 선언하고 new User()로 인스턴스를 만들면서도, 왜 메서드는 user 객체 안에 없는지, this가 왜 갑자기 undefined가 되는지 명쾌하게 설명하기 어려웠다면, 이 글이 그 막연함을 걷어줄 것이다. class 문법이 내부에서 어떻게 동작하는지, private field가 실제로 무엇이 다른지, 그리고 V8이 클래스 코드를 어떻게 최적화하는지까지 한 번에 다룬다.

기준: 『모던 자바스크립트 Deep Dive』의 클래스·프로토타입·상속 흐름을 바탕으로 정리하되, MDN과 V8 공식 문서의 내용을 함께 참고했다.

class는 prototype 모델의 현대적인 인터페이스다

JavaScript의 class는 Java나 C#의 클래스와 완전히 같지 않다. JavaScript는 본질적으로 프로토타입 기반 언어이고, class 문법 역시 그 프로토타입 모델 위에서 동작한다.

다만 "생성자 함수와 프로토타입을 보기 좋게 감싼 문법"으로만 이해하면 부족하다. 클래스는 다음과 같은 고유한 특징을 가진다.

  • 클래스 본문은 자동으로 strict mode로 실행된다.
  • 클래스는 new 없이 호출할 수 없다.
  • constructor, extends, super, static, #privateField 같은 전용 문법을 제공한다.
  • 클래스 메서드는 기본적으로 prototype에 정의되어 인스턴스 간에 공유된다.
class User {
  constructor(name) {
    this.name = name;
  }

  sayHello() {
    return `Hello, ${this.name}`;
  }
}

const user = new User("Kim");

console.log(user.name);       // Kim
console.log(user.sayHello()); // Hello, Kim

겉으로 보면 User 클래스에서 user 인스턴스를 만든 것처럼 보인다. 하지만 내부적으로는 user 객체가 User.prototype을 자신의 프로토타입으로 연결하고, sayHello 메서드는 user 객체가 아니라 User.prototype에 존재한다.

클래스는 결국 prototype chain으로 동작한다

JavaScript에서 객체는 다른 객체를 자신의 프로토타입으로 참조할 수 있다. 어떤 프로퍼티나 메서드를 찾을 때, 먼저 자기 자신을 확인하고 없으면 [[Prototype]]으로 연결된 객체를 따라 올라간다. 이 구조를 프로토타입 체인이라 한다.

const user = new User("Kim");

console.log(Object.getPrototypeOf(user) === User.prototype); // true
console.log(User.prototype.constructor === User);            // true

name은 인스턴스 자신의 프로퍼티고, sayHello는 인스턴스에 직접 들어 있지 않고 User.prototype에 존재한다.

console.log(user.hasOwnProperty("name"));     // true
console.log(user.hasOwnProperty("sayHello")); // false
console.log(User.prototype.hasOwnProperty("sayHello")); // true

user.sayHello()를 호출하면 엔진은 이 순서로 탐색한다.

user 객체에서 sayHello를 찾음
→ 없음
User.prototype에서 sayHello를 찾음
→ 있음 → 호출

extends를 사용하면 프로토타입 체인은 더 길어진다.

class Animal {
  move() {
    return "움직인다";
  }
}

class Dog extends Animal {
  bark() {
    return "멍멍";
  }
}

const dog = new Dog();

console.log(dog.bark()); // 멍멍
console.log(dog.move()); // 움직인다

이때 dog의 프로토타입 체인은 아래 구조를 가진다.

dog
→ Dog.prototype
→ Animal.prototype
→ Object.prototype
→ null

dog.bark()는 Dog.prototype에서 찾고, dog.move()는 Dog.prototype에 없기 때문에 한 단계 위인 Animal.prototype에서 찾는다.

JavaScript의 클래스 상속은 "설계도를 복사해서 인스턴스를 만든다"가 아니라, 객체와 객체를 프로토타입 체인으로 연결해서 동작을 위임하는 방식이다.

private field: 네이밍 컨벤션이 아니라 언어 차원의 제한

JavaScript에서는 오래전부터 _name 같은 이름으로 private를 흉내냈다.

class User {
  constructor(name) {
    this._name = name;
  }
}

하지만 _name은 실제 private가 아니다. 언더스코어는 "내부용입니다"라는 개발자 간의 약속일 뿐, 언어 차원에서 접근을 막아주지 않는다.

const user = new User("Kim");

console.log(user._name); // Kim
user._name = "Lee";
console.log(user._name); // Lee  — 외부에서 바꿀 수 있다

현대 JavaScript에서는 # 문법으로 진짜 private field를 선언할 수 있다.

class User {
  #name;

  constructor(name) {
    this.#name = name;
  }

  getName() {
    return this.#name;
  }
}

const user = new User("Kim");

console.log(user.getName()); // Kim
console.log(user.#name);     // SyntaxError

#name은 일반 프로퍼티가 아니다. 문자열 키로 접근하는 방식도 전부 막혀 있다.

console.log(user["#name"]); // undefined — 이건 "#name"이라는 키를 가진 공개 프로퍼티를 찾는 것
console.log(user["name"]);  // undefined — public "name" 프로퍼티가 없음 (#name과 별개)

중요한 점은 private field가 프로토타입 체인으로 상속되지 않는다는 것이다. 서브클래스에서도 부모 클래스의 private field에 직접 접근할 수 없다.

class Parent {
  #value = 1;
}

class Child extends Parent {
  getValue() {
    return this.#value; // SyntaxError
  }
}

부모 클래스의 #value를 사용하려면 부모 클래스가 public 메서드를 통해 노출해야 한다.

class Parent {
  #value = 1;

  getValue() {
    return this.#value;
  }
}

class Child extends Parent {
  printValue() {
    return this.getValue();
  }
}

const child = new Child();
console.log(child.printValue()); // 1

#privateField는 단순한 네이밍 컨벤션이 아니라 JavaScript 언어 차원에서 접근이 제한되는 진짜 private다.

클래스에서 this가 사라지는 경우

JavaScript에서 this는 "어디서 정의되었는가"보다 어떻게 호출되었는가에 따라 결정된다. 클래스 안에서도 이 원칙은 그대로 적용된다.

class User {
  constructor(name) {
    this.name = name;
  }

  sayHello() {
    return `Hello, ${this.name}`;
  }
}

const user = new User("Kim");

console.log(user.sayHello()); // Hello, Kim

user.sayHello()처럼 객체를 통해 호출하면 this는 user를 가리킨다. 하지만 메서드를 변수에 따로 할당한 뒤 호출하면 달라진다.

const sayHello = user.sayHello;

console.log(sayHello()); // TypeError: Cannot read properties of undefined

클래스 본문은 자동으로 strict mode로 실행된다. 그래서 메서드를 객체 없이 일반 함수처럼 호출하면 this는 전역 객체가 아니라 undefined가 된다. 이 문제를 해결하는 방법은 세 가지다.

bind로 this를 고정하기

const sayHello = user.sayHello.bind(user);

console.log(sayHello()); // Hello, Kim

클래스 필드와 화살표 함수 사용하기

class User {
  constructor(name) {
    this.name = name;
  }

  sayHello = () => {
    return `Hello, ${this.name}`;
  };
}

화살표 함수는 자신의 this를 만들지 않고, 생성 시점의 this를 렉시컬하게 캡처한다. React 컴포넌트나 이벤트 핸들러에서 자주 쓰이는 패턴이다.

다만 이 경우 sayHello는 User.prototype에 올라가지 않고 각 인스턴스마다 별도의 함수 객체로 생성된다. 편의성은 좋지만 인스턴스가 많아지면 프로토타입 메서드보다 메모리를 더 사용한다.

호출 시점에 객체를 유지하기

button.addEventListener("click", () => {
  user.sayHello();
});

user.sayHello() 형태로 호출되므로 this가 유지된다.

클래스에서 this는 인스턴스를 자동으로 고정하는 마법 같은 값이 아니다. 호출 방식에 따라 달라지며, strict mode 덕분에 잘못된 this 사용을 더 빨리 드러내줄 뿐이다.

V8이 클래스를 좋아하는 이유: Hidden Class

JavaScript 객체는 동적으로 프로퍼티를 추가하거나 삭제할 수 있다.

const user = {};

user.name = "Kim";
user.age  = 20;
user.job  = "developer";

이런 유연성은 장점이지만, 엔진 입장에서는 최적화가 어렵다. 객체마다 어떤 프로퍼티가 있고 메모리 어디에 있는지 매번 동적으로 찾아야 한다면 속도가 느려진다.

이를 해결하기 위해 V8 같은 엔진은 내부적으로 Hidden Class(또는 Shape)를 사용한다. Hidden Class는 객체가 어떤 프로퍼티를 가지고 있고, 각 프로퍼티가 내부 어디에 저장되어 있는지를 나타내는 엔진 내부의 구조다.

const user1 = { name: "Kim", age: 20 };
const user2 = { name: "Lee", age: 30 };

두 객체는 같은 구조를 가진다. 엔진은 이 둘이 같은 Hidden Class를 공유한다고 판단하고, user.name 접근 시 "이 구조에서 name은 특정 위치에 있다"는 정보를 캐싱해 더 빠르게 접근한다.

클래스는 이 최적화에 유리한 코딩 스타일을 유도한다.

class User {
  constructor(name, age) {
    this.name = name;
    this.age  = age;
  }
}

const user1 = new User("Kim", 20);
const user2 = new User("Lee", 30);
const user3 = new User("Park", 40);

생성자에서 항상 같은 순서로 같은 프로퍼티를 초기화하면 여러 인스턴스가 같은 Hidden Class를 공유하기 쉬워진다. 반대로 프로퍼티를 추가하는 순서가 객체마다 다르면 엔진이 형태를 예측하기 어려워진다.

const user1 = {};
user1.name = "Kim";
user1.age  = 20;

const user2 = {};
user2.age  = 30; // 순서가 다름
user2.name = "Lee";

두 객체는 최종적으로 같은 프로퍼티를 가지지만, 추가 순서가 다르기 때문에 엔진 내부에서는 다른 Hidden Class로 취급될 수 있다.

Hidden Class는 JavaScript 명세가 아닌 엔진 내부 최적화 기법이다. V8, SpiderMonkey, JavaScriptCore마다 이름과 세부 구현이 다르다. "Hidden Class를 직접 제어한다"기보다, 객체 구조를 일관되게 유지하면 엔진 최적화에 유리하다고 이해하는 편이 정확하다.

그러면 왜 prototype을 직접 쓰지 않는가

어차피 JavaScript 클래스도 prototype chain으로 동작한다면, 생성자 함수와 prototype을 직접 써도 되는 것 아닌가.

ES6 이전에는 실제로 이렇게 썼다.

function User(name) {
  this.name = name;
}

User.prototype.sayHello = function () {
  return `Hello, ${this.name}`;
};

const user = new User("Kim");
console.log(user.sayHello()); // Hello, Kim

동작은 같다. 하지만 class를 쓰는 이유는 분명하다.

의도가 명확하다. class, constructor, extends, super 키워드는 이 코드가 객체 생성 구조라는 사실을 한눈에 드러낸다. 생성자 함수와 prototype 조작이 섞인 코드에서는 이 코드가 일반 함수인지, 생성자인지, 메서드를 어디에 붙이는지 파악하는 데 더 많은 맥락이 필요하다.

실수를 줄여준다. 클래스는 new 없이 호출할 수 없다.

class User {}
User(); // TypeError

일반 생성자 함수는 new 없이 호출 시 strict mode가 아니면 전역 객체를 오염시킬 수 있다. 클래스는 이 실수를 언어 차원에서 막는다.

상속 문법이 간결하다. 생성자 함수 기반 상속은 prototype을 직접 연결해야 한다.

function Animal(name) { this.name = name; }
Animal.prototype.move = function () { return "움직인다"; };

function Dog(name) { Animal.call(this, name); }
Dog.prototype = Object.create(Animal.prototype);
Dog.prototype.constructor = Dog;
Dog.prototype.bark = function () { return "멍멍"; };

클래스를 쓰면 같은 구조를 훨씬 읽기 좋게 표현할 수 있다.

class Animal {
  constructor(name) { this.name = name; }
  move() { return "움직인다"; }
}

class Dog extends Animal {
  bark() { return "멍멍"; }
}

private field 같은 현대 문법을 쓸 수 있다. 생성자 함수로도 클로저나 WeakMap으로 private를 흉내 낼 수 있지만, #privateField만큼 언어 차원에서 명확하고 일관된 방식은 아니다.

정리

JavaScript의 class는 prototype chain을 대체하는 새로운 객체 모델이 아니다. 내부적으로는 여전히 prototype chain을 사용하고, 인스턴스 메서드는 ClassName.prototype에 저장되어 인스턴스 간에 공유된다.

하지만 class가 단순한 장식 문법인 것도 아니다. strict mode 강제, new 없이 호출 불가, constructor / super / extends 문법, 그리고 언어 차원에서 접근이 막히는 #privateField까지 — 이것들은 prototype을 직접 다룰 때는 얻을 수 없는 보장이다.

성능 관점에서도 클래스는 V8 같은 엔진이 Hidden Class를 활용해 최적화하기 좋은 패턴으로 코드를 유도한다. 생성자에서 프로퍼티를 일관된 순서로 초기화하는 습관만으로도 의미 있는 차이가 생길 수 있다.

결국 JavaScript 클래스를 제대로 이해하려면 class 문법만 외우는 것으로는 부족하다. prototype chain, this 바인딩, private field, 엔진 최적화 방식까지 함께 이해했을 때 클래스가 왜 이렇게 설계되었는지가 비로소 보인다.
