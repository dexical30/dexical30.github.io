JavaScript this 딥다이브: 바인딩 규칙에서 ECMAScript 명세, V8 내부까지

this를 "자기 자신을 가리키는 키워드"라고 외웠다가 콜백 안에서 undefined가 나와 멈칫한 경험이 있다면, 이 글이 그 이유를 설명해줄 것이다. 바인딩 규칙 네 가지를 외우는 것에서 한 발 더 나아가, ECMAScript 명세가 this를 어떻게 결정하는지, V8 엔진이 C++ 레벨에서 그것을 어떻게 구현하는지까지 함께 살펴본다.

this는 어디서 왔을까

자바스크립트는 1995년 Netscape에서 만들어졌다. 당시 "Java와 경쟁하지 않는 느낌의 언어"라는 비즈니스적 방향이 있었고, 그 결과 Java의 문법과 키워드가 상당 부분 흡수되었다. this도 그 흔적 중 하나다.

Java에서 this는 현재 클래스의 인스턴스를 가리키는 고정된 참조다. 그런데 자바스크립트는 클래스 기반 언어가 아닌 프로토타입 기반 언어이고, 함수가 일급 객체로 어디서든 전달될 수 있다. 이 차이가 this를 Java와 완전히 다른 동물로 만들었다.

자바스크립트의 this는 "자기 자신"이 아니라, 함수가 어떻게 호출되었느냐에 따라 값이 결정된다.

이 한 문장이 자바스크립트 this의 모든 것을 요약한다.

this가 왜 필요한가

MDN의 정의를 먼저 보자.

this 키워드는 코드 조각이 실행되는 컨텍스트를 가리킵니다. 가장 일반적으로는 객체 메서드에서 사용되며, 이때 this는 그 메서드가 속한 객체를 가리킵니다. 이를 통해 동일한 메서드를 서로 다른 객체에서 재사용할 수 있습니다.

객체지향 스타일로 코드를 작성하려면 자기 자신을 가리킬 수 있는 특별한 식별자가 반드시 필요하다. 아래 예시를 보면 직관적으로 이해된다.

function Circle(radius) {
    ???.radius = radius
}

Circle.prototype.getDiameter = function () {
    return 2 * ???.radius
}

const circle = new Circle(30)

??? 자리에는 "지금 생성되고 있는 객체"를 가리키는 무언가가 들어가야 한다. 인스턴스가 만들어지기 전에는 이름을 붙일 수도 없기 때문에, 호출 시점에 동적으로 자기 자신을 참조할 수 있는 키워드가 필요하다. 자바스크립트는 이 자리를 this로 채운다.

함수 호출과 함께 오는 암묵적 값들

this를 선언한 적 없는데 함수 안에서 쓸 수 있는 이유가 있다. 함수가 호출되는 순간, 자바스크립트 엔진은 우리가 작성하지 않아도 세 가지를 자동으로 만들어 함수 내부에 전달한다.

arguments
호출 시 전달된 모든 인수를 담는 유사 배열(array-like) 객체다. 매개변수로 명시하지 않은 인수도 여기 포함된다.

this
호출 방식에 따라 값이 달라지는 참조값이다. 단순 호출(fn())이면 globalThis, new 키워드로 호출하면 새로 생성된 빈 객체 {}가 들어온다.

new.target
이 함수가 new로 호출되었는지를 알려주는 메타 프로퍼티다. new로 호출하면 함수 자기 자신을, 일반 호출이면 undefined를 갖는다. 생성자로만 호출되도록 강제할 때 활용한다.

아래는 new 연산자 호출 시 내부에서 일어나는 일을 주석으로 풀어본 것이다.

function User(name) {
    // 1. 빈 객체 생성
    // this = {}

    // 2. prototype 연결
    // this.__proto__ = User.prototype

    // 3. 함수 본문 실행
    this.name = name;

    // 4. this를 자동 반환
    // return this
}

new User("devidi")를 호출하면 이 4단계가 내부적으로 실행된다. this를 명시적으로 만들거나 반환하지 않아도 되는 이유가 여기에 있다.

this 바인딩 규칙

"어떻게 호출되었느냐에 따라 this에 어떤 값이 들어가는지 결정되는 과정"을 **this 바인딩(this binding)**이라고 부른다. 크게 두 갈래다.

  • 암시적 바인딩: 호출 방식에 따라 엔진이 자동으로 결정
  • 명시적 바인딩: call, apply, bind로 개발자가 직접 지정

암시적 바인딩 4가지 패턴

1. 일반 함수 호출 — 기본 바인딩

fn() 형태로 그냥 호출하면 this는 전역 객체(globalThis)다. strict 모드에서는 undefined가 된다.

function showThis() {
    console.log(this);
}

showThis(); // 브라우저: window / Node: global / strict: undefined

이것이 가장 많은 실수의 원인이다. 메서드 안에 있는 중첩 함수도 "그냥 호출"이기 때문에 기본 바인딩이 적용된다.

const obj = {
    name: "devidi",
    outer() {
        function inner() {
            console.log(this); // window / undefined
        }
        inner(); // 일반 함수 호출
    },
};

obj.outer();

2. 메서드 호출 — 객체에 의한 바인딩

obj.method() 형태로 호출하면 this는 점(.) 앞의 객체가 된다.

const user = {
    name: "devidi",
    greet() {
        console.log(`Hi, I'm ${this.name}`);
    },
};

user.greet(); // Hi, I'm devidi  (this === user)

핵심은 this가 함수가 어디 정의되었는가가 아니라 어떻게 호출되었는가에 의해 결정된다는 것이다. 같은 함수도 호출 방식이 바뀌면 this가 바뀐다.

const greet = user.greet;
greet(); // Hi, I'm undefined  (this === globalThis)

user.greet를 변수에 담는 순간 "어떤 객체의 메서드"라는 맥락이 사라진다. 콜백으로 함수를 넘길 때 this가 사라지는 문제도 이 원리에서 비롯된다.

3. 생성자 호출 — new 바인딩

new 키워드와 함께 호출하면 앞서 본 4단계가 실행되면서 새로 생성된 빈 객체가 this에 바인딩된다.

function User(name) {
    this.name = name;
}

const u = new User("devidi");
console.log(u.name); // "devidi"

new로 호출하면 어떤 다른 바인딩 방식보다 우선한다.

4. 화살표 함수 — Lexical this

화살표 함수는 위 세 규칙과 완전히 다르게 동작한다. 자기 자신의 this를 가지지 않고, 자신이 정의된 시점의 외부 스코프(렉시컬 스코프)의 this를 그대로 쓴다.

const user = {
    name: "devidi",
    greet() {
        const arrow = () => {
            console.log(this.name); // greet의 this를 그대로 사용
        };
        arrow();
    },
};

user.greet(); // "devidi"

이 덕분에 콜백에서 this가 사라지는 문제를 해결할 때 화살표 함수가 자주 쓰인다. 반대로, 객체 메서드 자체를 화살표 함수로 정의하면 this가 객체가 아닌 외부(보통 모듈/전역)를 가리키게 되므로 주의해야 한다.

const user = {
    name: "devidi",
    greet: () => console.log(this.name), // this !== user
};

명시적 바인딩

Function.prototype에 정의된 세 메서드로 this를 직접 지정할 수 있다.

call(thisArg, ...args)

함수를 즉시 실행하면서 this와 인자를 직접 넣는다.

function introduce(greeting) {
    console.log(`${greeting}, I'm ${this.name}`);
}

const user = { name: "devidi" };
introduce.call(user, "Hi"); // Hi, I'm devidi

apply(thisArg, argsArray)

call과 거의 같지만 인자를 배열로 전달한다. 인자 개수가 가변적일 때 유용하다.

introduce.apply(user, ["Hello"]); // Hello, I'm devidi

bind(thisArg, ...args)

함수를 즉시 실행하지 않고, this가 고정된 새 함수를 반환한다. 콜백처럼 나중에 호출될 함수의 this를 미리 묶어 둘 때 가장 자주 쓴다.

const boundIntroduce = introduce.bind(user, "Hey");

boundIntroduce();             // Hey, I'm devidi
setTimeout(boundIntroduce, 1000); // 1초 뒤에도 this는 user

bind로 한 번 묶인 함수의 this는 이후 call이나 apply로도 바꿀 수 없다. bind가 가장 강한 명시적 바인딩이다.

바인딩 우선순위

다이어그램 로딩 중...

화살표 함수는 이 우선순위 체계에 아예 들어가지 않는다. 자체 this가 없기 때문에 call, apply, bind를 써도 this를 바꿀 수 없다.

const arrow = () => console.log(this);
arrow.call({ name: "devidi" }); // call의 인자 무시, 외부 this 사용

한 줄 요약:

**"어떻게 호출되었는가"**가 this를 결정한다. 단, 화살표 함수만 예외로 **"어디서 정의되었는가"**를 따른다.

ECMAScript 명세로 보는 this

바인딩 규칙을 이해했다면, 이제 명세가 이것을 어떻게 정의하는지 보자. 사양서의 언어로 읽으면 "엔진이 실제로 무엇을 하는가"가 보이기 시작한다.

실행 컨텍스트란

자바스크립트는 코드 실행을 추적하기 위해 **실행 컨텍스트(Execution Context)**를 사용한다. 컨텍스트는 다음을 추적한다.

  • 코드 평가 상태 (어디까지 실행됐는지)
  • 변수 바인딩 (변수 이름과 값의 연결)
  • this 참조

함수가 호출될 때마다 새 실행 컨텍스트가 생성되어 **실행 컨텍스트 스택(Call Stack)**에 쌓이고, 함수가 종료되면 스택에서 제거된다.

환경 레코드(Environment Record) 타입 계층

명세는 스코프를 환경 레코드라는 추상 타입으로 표현한다. 계층 구조는 다음과 같다.

다이어그램 로딩 중...

각 환경 레코드가 this 바인딩을 갖는지 여부가 중요하다.

환경 레코드 종류this 바인딩
Function있음 (단, 화살표 함수는 없음)
Global있음 (전역 객체)
Module있음 (undefined)
Object (with)없음
Declarative (let/const)없음

모든 환경 레코드는 [[OuterEnv]] 필드를 가지며, 이것이 바깥쪽 환경 레코드를 가리킨다. 변수를 찾을 때 이 체인을 따라 올라가는 것이 우리가 "스코프 체인"이라 부르는 것의 실체다.

this가 결정되는 알고리즘: 3단계 흐름

this를 참조하는 코드를 만나면 명세는 세 단계를 밟는다.

다이어그램 로딩 중...

ResolveThisBinding()이 GetThisEnvironment()를 호출하고, 거기서 HasThisBinding()이 true인 환경 레코드를 찾을 때까지 [[OuterEnv]] 체인을 거슬러 올라간다. 루프가 반드시 종료되는 이유는, 최상위에 항상 this 바인딩을 갖는 전역 환경 레코드가 있기 때문이다.

화살표 함수가 왜 this를 캡처하는가

화살표 함수의 Function Environment Record는 HasThisBinding()이 false를 반환한다. 따라서 GetThisEnvironment()는 화살표 함수 자신의 환경 레코드를 건너뛰고 바깥 환경으로 올라간다. 이것이 "정의된 위치의 this를 사용한다"는 동작의 실제 메커니즘이다.

스코프 체이닝: [[OuterEnv]]의 정체

명세 본문에 "Scope Chain"이라는 단어는 공식 용어로 정의되어 있지 않다. 대신 [[OuterEnv]] 필드를 통한 중첩 구조로 설명한다.

변수를 찾는 GetIdentifierReference 알고리즘도 구조는 같다.

  1. 현재 환경에 찾는 식별자가 있는지 확인
  2. 없으면 [[OuterEnv]]로 이동
  3. 찾거나 null에 도달할 때까지 반복

이 "바깥으로 타고 올라가는 반복 과정"이 스코프 체이닝의 알고리즘적 정의다. 명세가 비유 대신 데이터 구조로 설명하는 이유는, 엔진 개발자가 실제로 구현할 수 있을 만큼 정교해야 하기 때문이다.

V8 엔진 내부: this는 어떻게 구현되는가

명세가 "무엇을"인지를 정의한다면, V8은 "어떻게"를 구현한다. V8은 이 두 레이어를 명확히 분리한다.

다이어그램 로딩 중...

V8 소스 주석에 이것이 명시되어 있다.

"JS environments are represented in the parser using Scope, DeclarationScope, and ModuleScope"
— JS의 환경(Environment)이 파서에서는 Scope로 표현된다는 의미다.

즉, 하나의 개념이 두 레이어로 분리된다: 컴파일 타임의 Scope와 런타임의 Context.

DeclareThis: 컴파일 타임에 this 변수를 선언하는 곳

src/ast/scopes.cc의 DeclareThis()가 this 변수를 어느 스코프에 배치할지 결정한다.

void DeclarationScope::DeclareThis(AstValueFactory* ast_value_factory) {
  DCHECK(!already_resolved_);
  DCHECK(is_declaration_scope());
  DCHECK(has_this_declaration());
  bool derived_constructor = IsDerivedConstructor(function_kind_);
  Variable* var =
      Declare(zone(), ast_value_factory->this_string(),
              derived_constructor ? CONST : VAR, THIS_VARIABLE,
              derived_constructor ? kNeedsInitialization : kCreatedInitialized);
  receiver_ = var;
}

파생 클래스 생성자(derived_constructor)인 경우 CONST로 선언해서 super() 호출 전에 this를 쓰면 에러가 발생하도록 한다. 일반 함수는 VAR로 선언된다.

마무리

this가 헷갈리는 근본 이유는 하나다. 자바스크립트의 this는 정의된 위치가 아니라 호출 방식에 의해 결정되도록 설계되었기 때문이다. 화살표 함수만 이 규칙의 예외로, 정의된 위치의 렉시컬 this를 따른다.

ECMAScript 명세는 이것을 GetThisEnvironment()가 [[OuterEnv]]를 타고 HasThisBinding()이 true인 환경을 찾는 알고리즘으로 정의한다. V8은 이것을 컴파일 타임(Scope)과 런타임(Context) 두 레이어로 분리해 구현하고, 화살표 함수의 this 캡처를 컴파일 타임에 처리한다.

바인딩 규칙 네 가지를 외우고 있다면, 이제 그 규칙이 왜 그렇게 동작하는지도 설명할 수 있을 것이다.
